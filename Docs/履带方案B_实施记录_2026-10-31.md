## 1. 上一轮为什么卡住（根因）

上一轮把问题当成「Unity 里怎么驱动」来解决，实际缺陷全在**资产层**：

| 现象 | 真正原因 |
|---|---|

## 2. 现在的实现

### 2.1 Blender：`work/build_tracks3.py`

```powershell
# 用法：blender -b --python work\build_tracks3.py -- <name> <槽长> <槽高> <槽宽> [源模型名] [--render]
blender -b --python work\build_tracks3.py -- main  8.286 1.915 4.153 --render
blender -b --python work\build_tracks3.py -- light 7.021 1.554 3.943 main --render
blender -b --python work\build_tracks3.py -- heavy 10.098 2.935 5.412 main --render
```

流程：
1. 载入 `<源>_tracks_only_parts.glb`（part_split 的 20 个零件，每块都是面片汤）。
2. 归一化：长轴→Y；缩放按「履带槽宽 / 槽高」的**几何平均**（等比例，轮子不会被压成椭圆）。
3. 零件分类：沿 Y 很长 = 履带板；YZ 平面圆乎乎 + 侧向薄（或横跨左右）= 轮子候选。
4. 轮子候选 → **截尾均值**求轴心（反复丢掉最外 35% 的连通块，把粘上来的碎片甩掉），
   半径取保留块顶点径向距离的 p98；双联轮按 Y 一分为二，跨左右的一对按 X 正负分开。
5. 过滤假轮子：内圈面占比 < 0.10（履带端部弧带不是圆盘）、超出履带环、面数 < 150 的一律丢。
6. **按面分配**：离轴心径向 ≤ 1.04R（再按 p96 收一遍）且在自己 x 带宽内 → 该轮子；
   其余 → **静态组**（不再塞回履带，塞回去会把面扯成长条）。
7. 每个轮子原点搬到轴心；履带按 X 正负分成 `belt_L` / `belt_R`。
8. **先导出 FBX，再上色渲染**（顺序反了 FBX 里会带调试纯色材质）。
9. 输出报告 `ArtSource/Lux3D/<name>_tracks3_report.json` + 三张核对图
   `work/shots/tracks3_<name>_{side,wheels,belts}.png`。

### 2.2 Unity：`Assets/Scripts/Units/TrackAssembly.cs`（重写）

- **轮子**（`wheel*`）：绕自身局部 X 轴转，`ω = v / R`，R 取网格包围盒短边的一半。
- **履带**（`belt*`）：**沿环路径真位移**，不是滚贴图：
  1. 先用包围盒跑道形粗筛出履带板本体的顶点；
  2. **质心 + 按角度分箱取均值** → 得到环的真实中心线（环是凸的，角度对弧长单调）；
  3. 按弧长均匀重采样成 256 点；
  4. 每个顶点：角度 → 弧长参数 `s` → 相对中心线的偏移 `(offY, offZ)`；
  5. 每帧 `s' = s + 走过的距离`，位置 = `中心线(s') + 旋转(偏移, Δ切线角)`，法线同样转。
- 距离相机 > 150 m 的坦克不逐帧算（省 CPU）；车速≈0 时直接跳过。
- 编辑器验证接口：`DebugSetup()` / `DebugAdvance(m)` / `DebugReset()`。

## 6.5 差速转向（2026-11-01 00:00 前加）

履带车不是靠打方向盘转的，是靠**左右履带速度差**：

```
左履带线速度 = 车速 + 偏航角速度 × 半轮距
右履带线速度 = 车速 − 偏航角速度 × 半轮距
```

- 右转（yaw 增大）：左履带往前、右履带往后 ✔
- 左转：左履带往后、右履带往前 ✔
- 原地转：车速 0，两侧等速反向 ✔

实现：`TrackAssembly.Update()` 里用 `Mathf.DeltaAngle(上一帧yaw, 当前yaw)` 算偏航角速度
（不依赖输入，AI 开的车也一样有效），左右两侧各自累加自己的滚动距离、各自的轮子按各自
线速度转。半轮距从履带网格包围盒中心的 x 反推。

验证：`DebugAdvanceSides(0.5f, -0.5f)` → 左履带平均位移 0.509 m、右履带 0.506 m ✔

## 6.6 性能：目前是这一项的最大短板

履带位移是**逐帧改顶点**（CPU），实测：

| 版本 | 每帧耗时（编辑器 Mono） |
|---|---|
| 初版（2 万顶点/条，含法线） | 23.5 ms |
| 去掉 RecalculateBounds + 预计算切线角 + SetVertices | 12.1 ms |
| 顶点焊接（Blender 侧 18091→7328） | **无效** —— Unity 按 UV 缝重新拆点，导入后还是 17962 个 |

打包是 IL2CPP，实测值一般比编辑器快 2~4 倍，估计 3~6 ms/台。场景里同时只有 1~2 台在
150 m 内（`animateDistance`），所以能跑，但**再往上加车就会掉帧**。

试过但没走通的一条路（代码留在 `Assets/Shaders/TrackBelt.shader` + `useGpuShader` 开关，默认关）：

- 思路：顶点着色器里按「中心线数据」推进，CPU 每帧只改一个 `_Scroll`，实测 **0.016 ms/帧**（快 750 倍）
- 卡点：中心线数据传不进 shader —— 先用 1×256 的 `RGBAFloat` 贴图 `tex2Dlod` 采样，再用
  `SetVectorArray` 传 256 个 float4，两种方式在顶点着色器里读出来都是 0（uv2 通道本身是好的，
  常量位移能生效）。**下次接手先写一个「把采样值直接输出成颜色」的最小复现**，定位是绑定问题
  还是 surface shader 顶点阶段的问题，通了就能把性能问题彻底解决。

## 6.7 GPU 顶点动画跑通 + 清碎片（2026-11-01 上午）

### 结论先放这儿

| 项 | 结果 |
|---|---|
| 一台车履带每帧耗时 | CPU **10.4 ms** → GPU **0.005 ms**（≈1900 倍） |
| GPU 与 CPU 是否一致 | 推进 0 / 0.5 / 1.0 / 2.5 m，平均色差 **0.34~0.51 / 255**，明显不同像素 ≤1.3% |
| 三台车是否都走 GPU | light / main / heavy 都是 17 轮 + 2 条履带，走 Shader **2/2** |
| Play 模式实测 | 材质 = `Tank/TrackBelt`、UV2 有数据、2 秒内画面 3.76% 像素在变（履带确实在动） |

### 昨天"读出来是 0"到底怎么回事

写了个最小复现（`_TestPath` / `_TestPathSurf`，验证完已删），同一份数据用两种方式读：

| 方式 | 结果 |
|---|---|
| 普通 vertex/fragment shader + `material.SetVectorArray` | (0.40, 0.60, 0.70) ✔ 与期望一致 |
| 同上 + `material.SetTexture` 顶点采样 | ✔ 一致（注意滤波会插值，测的时候用 Point） |
| **surface shader** + `SetVectorArray` + `SetTexture` | ✔ **也一致** |
| 全局 `Shader.SetGlobalTexture` | ✘ 读到 0（全局数组是好的） |

→ **Unity 6.3 Built-in 的 surface shader 顶点阶段绑定没问题**，昨天卡住是旧代码本身的问题
（旧 shader 里还留着 `v.vertex.x += _PathArr[3].y * 30.0` 之类的调试位移，读 0 说明当时设的
材质不是实际渲染用的那个 / 或 `_belts` 为空时 SetupGpu 根本没跑）。

### 现在的实现

- `TrackBelt.shader`：`UV2.x` = 弧长参数（0~1），`UV2.y` = 该顶点是否参与运动（0 = 碎片，原样输出）；
  `_PathArr[256]` 传中心线 `(0, y, z, 切线角)`；顶点着色器做「中心线插值 + 偏移按角差旋转」，
  法线同样旋转。CPU 每帧只写一个 `_Scroll`。
- `TrackAssembly.SetupGpu()`：写 UV2、建每条约 1 个材质实例（复制原材质的贴图/颜色/光滑度/金属度）。
- **`Tank/TrackBelt` 已加入 Project Settings → Graphics → Always Included Shaders**，
  否则打包时会被剔除，运行时 `Shader.Find` 返回 null 静默退回 CPU。
